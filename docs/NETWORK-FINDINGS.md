# 校园网连通性实测结论

> 2026-11-10 · 上海交通大学（SJTU）无线网 · 实测而非推测

## 测试环境

| 项 | 值 |
|---|---|
| PC | `10.180.211.30/15`，网关 `10.180.0.1`，无线网卡 |
| PC IPv6 | `2403:d400:1000:12:be59:8702:d4f4:f123` |
| 手机 | Pixel 6a，`10.180.231.235/15`，SSID `SJTU`，RSSI -48，816 Mbps |
| 手机 IPv6 | `2403:d400:1000:12:5ac4:6a7a:f2d8:e6aa`（与 PC 同一 /64） |
| Windows 网络配置 | `SJTU 3` / WLAN / **Public** |

注意：两台设备的 IPv4 在同一 /15 内，IPv6 在同一 /64 内。**物理上就是邻居。**

## 测试结果

| # | 测试 | 命令 | 结果 | 判读 |
|---|---|---|---|---|
| 1 | 手机 → PC IPv4 | `ping -c 3 10.180.211.30` | `Destination Host Unreachable`，100% 丢包 | ARP 解析失败 |
| 2 | 手机 → 网关 | `ping -c 3 10.180.0.1` | 12–46 ms，0% 丢包 | 出站正常 |
| 3 | 手机 → PC IPv6 | `ping6 -c 3 2403:...:f123` | `Address unreachable`，100% 丢包 | NDP 解析失败 |
| 4 | 手机 → 公网 IPv6 | `ping6 -c 2 2400:3200::1` | 15–19 ms，0% 丢包 | IPv6 出网正常 |
| 5 | PC → 手机 IPv6 | `ping -6 2403:...:e6aa` | 100% 丢包 | 双向都不通 |
| 6 | 手机 → PC TCP 8080 | `nc -w 3 2403:...:f123 8080` | `No route to host` | — |

## 结论

**SVTI 校园无线网启用了客户端隔离（client isolation / AP isolation），且对 IPv4 与 IPv6 同时生效。**

- 同一网段、同一 /64 的任意两台终端之间**完全不可互访**
- 出站到网关、公网（v4 NAT / v6）均正常
- 这意味着 ROADMAP 里的降级阶梯 **① 同网段直连** 与 **② 公网 IPv6 直连** 两条全部作废

### 一个容易误判的插曲

放行防火墙之前，App 报的是「超时」；放行之后变成「拒绝连接」。看起来像是防火墙的问题解决了，
实际上只是超时被判成了连接拒绝 —— **两种表现都指向同一个根因：包根本没到对方**。
教训：`ECONNREFUSED` 不等于「对端没开服务」，在隔离网络里它也可能来自中间设备或本机协议栈的伪造响应。

### 防火墙确实也有问题（已修）

即使隔离不存在，按当时的配置也连不上：

- Windows 把该 WiFi 判为 **Public** 配置文件，入站默认拦截
- 已有的 `python.exe` 放行规则都是**按程序路径**匹配的：`python310`、`miniconda`、
  `trae solo`、`workbuddy\resources\vendor\python`
- 实际运行的是 `.workbuddy\binaries\python\versions\3.13.12\python.exe` —— **没有任何规则覆盖**
- 已用 `tools/open-firewall.bat` 添加按端口放行的规则（TCP 8080/8443，Private + Public）

这条修复对后续走 Tailscale / 热点依然必要，不是白做。

## 可行的替代路径

| 顺位 | 方案 | 预期延迟 | 代价 |
|---|---|---|---|
| ③ | **Tailscale**（WireGuard） | 30–80 ms（大概率走 DERP 中继，因为双方都无公网可达端口） | PC 与手机各装客户端，登录同一账号 |
| ④ | 自建 VPS 中继 | 50–150 ms | 一台服务器 + 运维 |
| 兜底 | **手机开热点，PC 连热点** | 5–10 ms | 无需任何第三方；PC 保留校园网为默认路由 |
| 临时 | USB + `adb reverse` | 2–4 ms | 只适合调试，不能当产品形态 |

**建议先用「兜底」验证功能闭环**（零成本、低延迟、可控），再用 Tailscale 验证「无线可用」。

## 对产品的影响

这不是一个可以绕过的环境问题，它直接约束产品定位：

1. **不能假设「同一 WiFi 就能直连」**。必须内置连接方式探测与降级，并在 UI 上明确告知用户当前走的是哪一级。
2. **配对与发现机制必须能工作在不支持广播/mDNS 的网络里** —— 实测 mDNS 也没有响应。
   所以二维码扫码配对（把 endpoint 直接编进二维码）不是"锦上添花"，是**必需**的。
3. **中继路径的延迟（30–150 ms）决定了产品边界**：仪表显示没问题，
   但密集操作会明显迟滞。ROADMAP §6 里「关键 HOTAS 不上平板」的判断被这次实测坐实了。

# 第二轮：PC 移动热点（2026-11-10 18:45–19:05）

校园网隔离之后试的第一条替代路径：**PC 开移动热点，手机连它**。

## 好消息：并发是真的

```
WLAN   (主接口)  → 仍连着 SJTU，1201 Mbps，ch52
WLAN 5 (虚拟口)  → 热点，192.168.137.1/24，ch153
```

MT7925 驱动提供 5 个虚拟接口，**STA + AP 并发成立** —— PC 既不掉校园网，又能当 AP。
手机拿到 `192.168.137.141`，RSSI -31 dBm，链路 11ax。

## 坏消息：延迟不可接受

| 测量 | 结果 |
|---|---|
| PC → 手机 ICMP（20 次） | 最小 **4 ms** / 平均 **115–136 ms** / 最大 **299–401 ms**，0% 丢包 |
| 应用层 RTT | 97 / 630 / 900 ms 之间乱跳 |
| 手机上报的链路 | Tx 32 Mbps、Rx 1200 Mbps、**重传率 15%** |
| 服务端本地响应（排除服务端） | 最小 1.3 ms / 平均 4.5 ms / 最大 56 ms |

最小值 4 ms 证明链路本身能跑满速；平均值和最大值说明有周期性停顿。

## 排查过程（三个假设，只成立一个）

| 假设 | 做法 | 结果 |
|---|---|---|
| TCP Nagle + 延迟 ACK | 服务端加 `disable_nagle_algorithm = True` | **部分成立**：900 → 97 ms，但没解决 |
| 信道冲突（STA ch52 vs AP ch153） | 断开 SJTU，让射频专职 AP | **不成立**：仍 631 ms |
| 手机 Wi-Fi 省电（DTIM 缓存） | 持 `WIFI_MODE_FULL_LOW_LATENCY` WifiLock | **不成立**：仍 136 ms 平均 |

## 结论

**Windows 移动热点（MediaTek MT7925）不适合做实时外设链路。**
疑似 AP 侧周期性扫描/调度造成的 100–400 ms 停顿 —— 这是 Windows 热点实现的特性，
应用层无法优化掉。

它仍然证明了「无线链路能跑通」，但**不能作为产品形态**。

## ★ 一个必须写进产品的坑：Android 会绕开「无互联网」的 Wi-Fi

热点没有互联网 → Android 把它标记为 unvalidated → **应用默认仍绑定蜂窝网络**。
此时发往 `192.168.137.1` 的包会从蜂窝接口出去（实测源地址 `10.153.183.186`），永远到不了 PC。

现象是「连接超时」，和「防火墙拦截」「服务没开」完全一样，极难区分。

**解法（已实现）**：目标为私有地址时，调用
`ConnectivityManager.bindProcessToNetwork(wifiNetwork)` 把进程绑定到 Wi-Fi。
这会写进产品代码，不是 workaround —— 任何「直连局域网设备」的场景都会遇到。
