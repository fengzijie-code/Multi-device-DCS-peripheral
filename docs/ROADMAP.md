# 多端 DCS 外设 · 项目阶段计划书

> 版本 0.1 · 2026-11-10
> 形态：DCS 在 Windows 本地运行；Pixel / iPhone / iPad 通过无线网络作为外设终端，既能看仪表，也能反向操作座舱。

---

## 0. 这份文档解决什么

它不是为了描述愿景，而是为了回答三个执行层面的问题：

1. **每个阶段结束时，必须能演示什么？**（退出准则）
2. **哪些工作可以在没有 DCS 的情况下推进？**（任务表里的「需 DCS」列）
3. **哪些事现在不做？**（范围护栏，防止项目失控）

范围一旦滑走，这个项目会变成一个无底洞——DCS 有几十个模组、上百个面板、上千个开关。**能否收敛取决于敢不敢划死边界。**

---

## 1. 目标与边界

### 1.1 产品目标

把手机/平板变成 DCS 的第二块、第三块、第四块座舱面板：

- **能看**：仪表、警告灯、MFCD 与 HUD 的真实画面
- **能操作**：座舱开关、旋钮、UFC/CDU 键盘、MFCD 边框键
- **能跨网**：在开启客户端隔离的校园网下依然可用
- **能加密**：链路上任何第三方都无法伪造或窃听

### 1.2 明确的非目标

| 不做 | 原因 |
|---|---|
| VR / 头显支持 | 与「手持触摸屏」形态正交，且工程量大一个量级 |
| 语音通讯的替代实现 | 只做 SRS 的 PTT 桥接，不重造语音链路 |
| 跨公网的观战、直播、云游戏 | 不是这个项目的问题 |
| 实体硬件（PCB、编码器、面板） | 纯软件项目，硬件另立 |
| MOD 机型的官方支持 | 只提供 community profile 机制，不做官方适配承诺 |
| iOS 端在 P4 之前启动 | 先把 Android + 桌面桥接做扎实，避免双端并行拖慢 |
| 关键 HOTAS 动作上平板 | 扳机、投放、抛撒、配平留在物理摇杆，见 §6 |

## 2. 核心假设

假设不是事实。下面每一条都标了验证时机和「若不成立」的退路。

| # | 假设 | 何时验证 | 若不成立 |
|---|---|---|---|
| A1 | 校园网至少有**一种**路径能让两台设备互相可达 | P0 | 退到手机热点兜底，项目仍可交付 |
| A2 | DCS 的 `Export.lua` 能在目标场景下加载并发送 UDP | P0 | 检查 `Scripts/` 权限与 Pure Client 设置 |
| A3 | `LoGet*` 能提供姿态、空速、高度、发动机等基础量 | P0 | 降级为仅 DCS-BIOS 通道 |
| A4 | DCS-BIOS 或自研解析器能覆盖目标机型的 clickable 表 | P2 | 该机型降为只读，`capabilities` 标记 |
| A5 | Android 设备支持低延迟硬件解码 | P3 | 软解兜底 + 降分辨率 |
| A6 | QUIC 在 Android 上可用（Cronet / kwik） | P1 | 退到 WSS over TLS 1.3，仍满足加密要求 |
| A7 | 单人业余投入可以维持节奏 | 全程 | 砍 P5，P4 只做两套 Profile |

## 3. 里程碑总览

| 阶段 | 名称 | 规模 | 粗估 | 需 DCS | 核心产出 |
|---|---|---|---|---|---|
| **P0** | 连通性验证 | S | 3–5 人日 | 部分 | 网络探测报告 + 最小闭环 |
| **P1** | 协议与渲染骨架 | M | 10–14 人日 | 否 | Proto 定型 + 6 个 widget + mock 源 |
| **P2** | 双向回控与安全 | L | 12–16 人日 | 是 | 配对体系 + ControlRef + 看门狗 |
| **P3** | MFCD / HUD 像素流 | L | 15–20 人日 | 是 | 低延迟视频链路 |
| **P4** | 布局编辑器与多机型 | XL | 20–25 人日 | 是 | 可视化配置 + 三套 Profile + iPad |
| **P5** | 触感与扩展 | M | 10–15 人日 | 是 | 震动、地图、SRS PTT |

> 粗估按单人业余投入折算，含调试与返工。总量约 70–95 人日，**不要拿它当承诺，拿它当排序依据**。

依赖关系：

```
P0 连通性
 └─► P1 协议与渲染 ─┬─► P2 双向与安全 ─┐
                    └─► P3 像素流 ─────┴─► P4 布局与多机型 ─► P5 触感与扩展
```

**关键路径是 P0 → P1 → P2**。P3 可以与 P2 并行，但两者都会在 P4 汇合。

## 4. 阶段详述

### Phase 0 · 连通性验证（Spike）

**目标**：用最小代码回答两个问题——(a) 你的校园网能走四级阶梯的哪一级；(b) 从 DCS 帧到手机像素的链路能否压在 100 ms 内。

**这个阶段唯一的目的是消除最大的未知，不追求任何工程质量。**代码可以丑，可以硬编码，可以写完就扔。

| # | 任务 | 需 DCS | 产出 |
|---|---|---|---|
| 0.1 | 网络探测脚本：同网段 ping、IPv6 前缀与可达性、UDP 双向、mDNS、出站策略 | 否 | `tools/netprobe/` |
| 0.2 | mock 导出源：按 `LoGet*` 字段结构以 60 Hz 发 UDP | 否 | `tools/mock-export/` |
| 0.3 | 最小 `Export.lua`：只发 alt / ias / pitch / bank 四元组 | 是 | `dcs/Export.lua` |
| 0.4 | Rust 极简 QUIC 服务：单流、无鉴权、直吐快照 | 否 | `bridge/` |
| 0.5 | Android 极简客户端：四个数字 + 连接状态 | 否 | `android/` |
| 0.6 | Tailscale 三端实测，记录打洞成功率与 RTT 分布 | 否 | `docs/NETWORK-PROBE.md` |
| 0.7 | 热点兜底验证：PC 双出口 + 接口跃点调优 | 否 | 同上 |

**退出准则**

- [ ] Pixel 屏幕上的数字随 DCS（或 mock）实时变化，p95 端到端 ≤ 100 ms
- [ ] `docs/NETWORK-PROBE.md` 记录四级阶梯的实际可用层级与实测 RTT 分布
- [ ] 断网 5 秒后恢复，重连 ≤ 3 s 且无需人工干预
- [ ] 热点兜底路径走通，且 PC 默认路由仍为校园网

**明确不做**：UI 美化、配对、DCS-BIOS、视频、多机型、错误处理。

### Phase 1 · 协议与渲染骨架

**目标**：把「数据长什么样」「界面怎么描述」两件事定死，然后让六个 widget 跑在 mock 源上。

| # | 任务 | 需 DCS | 产出 |
|---|---|---|---|
| 1.1 | `proto/` 定型：Handshake / Snapshot / Delta / Cmd / Ack / ControlRef / Profile | 否 | `proto/*.proto` |
| 1.2 | Profile JSON Schema + 校验器（含 `capabilities`、`requires`、版本号） | 否 | `schema/` |
| 1.3 | mock 源升级：支持卡顿、丢帧、断连、数值抖动、NaN 注入 | 否 | `tools/mock-export/` |
| 1.4 | Compose 渲染引擎：WidgetRegistry + 布局求解 + DPI 缩放基准 | 否 | `android/ui/` |
| 1.5 | 六个基础 widget：Tape / Gauge / Lamp / Toggle / Button / Keypad | 否 | `android/widgets/` |
| 1.6 | 录制回放器：把真机遥测存为 jsonl，测试时按原时间轴回放 | 录制需 | `tools/replay/` |
| 1.7 | 一套 F-16C Profile（标识符先用占位） | 否 | `profiles/f16c/` |

**退出准则**

- [ ] 同一份 Profile 在 6 种屏幕宽度、横竖屏下都不越界、不重叠、不互相遮挡
- [ ] 60 Hz 快照下 Pixel 掉帧率 < 1%，UI 线程 CPU 占用 < 15%
- [ ] 随机增删 50 次 widget 实例不崩溃，且布局自动重排正确
- [ ] 回放器能把一段 10 分钟的录制按原时间轴忠实重现，时间偏差 < 20 ms
- [ ] **新增一个 widget 实例只需要改 Profile，不需要改代码、不需要重装 APK**

**明确不做**：真实 DCS 数据（除录制）、配对、视频、MFCD。

### Phase 2 · 双向回控与安全

**目标**：让 Pixel 上点一下，DCS 座舱里那个开关真的翻过去；同时保证链路上没人能伪造这件事。

| # | 任务 | 需 DCS | 产出 |
|---|---|---|---|
| 2.1 | 自签 CA + Ed25519 设备证书 + 二维码配对流程 | 否 | `bridge/pairing/` |
| 2.2 | 证书固定、设备吊销、审计日志 | 否 | `bridge/security/` |
| 2.3 | `ControlRefProvider` trait + `DcsBiosProvider`（读生成物） | 否 | `bridge/controlref/` |
| 2.4 | `ClickableParser`：解析 `clickabledata.lua`，先覆盖 set / click / fixed-step 三类 | 否 | 同上 |
| 2.5 | Cmd 通道：单调序号、去重窗口、ack、超时重传 | 否 | `bridge/cmd/` |
| 2.6 | 看门狗 + 轴回中 + 按键释放 | 否 | 同上 |
| 2.7 | 真机接入 DCS-BIOS，校准标识符与取值域 | 是 | `docs/CONTROLREF-NOTES.md` |

**退出准则**

- [ ] 扫码到可用 ≤ 15 秒
- [ ] 伪造服务端（ARP 欺骗或改 pin）时连接被拒，客户端明确提示「证书不匹配」
- [ ] 用 `openssl s_client` 直连必须失败
- [ ] 强杀客户端进程 → 150 ms 内所有下发量归零，DCS 侧可见
- [ ] 开关双向闭环：点 → 座舱 3D 动 → 状态回传 → UI 变亮，往返 ≤ 120 ms
- [ ] 同一 Cmd 重放 100 次，座舱状态只变化一次

### Phase 3 · MFCD / HUD 像素流

**目标**：把 MFCD 的真实画面低延迟送到 Pixel 上，并且触摸边框键能命中。

**这是全项目工程量最大、最容易低估的一块。**

| # | 任务 | 需 DCS | 产出 |
|---|---|---|---|
| 3.1 | `MonitorSetup.lua` 生成器（把 MFCD 视口渲染到指定区域） | 否 | `bridge/mfcd/setup-gen` |
| 3.2 | Windows Graphics Capture 抓取指定区域 | 是 | `bridge/capture/` |
| 3.3 | 硬编码链路：NVENC / AMF，核显走 QuickSync，兜底 x264 ultrafast | 部分 | `bridge/encode/` |
| 3.4 | 传输：QUIC 独立流 + 简单拥塞控制 | 否 | `bridge/stream/` |
| 3.5 | Media3 低延迟解码（含软解兜底） | 否 | `android/video/` |
| 3.6 | 触摸热区 → MFCD 边框键映射 | 否 | `android/mfcd/` |
| 3.7 | 降级策略：带宽不足时降分辨率 / 降帧 / 切帧内刷新 | 否 | `bridge/stream/` |

**退出准则**

- [ ] 1080p30 端到端（PC 出图 → Pixel 显示）≤ 120 ms p95
- [ ] 单路带宽 ≤ 8 Mbps
- [ ] 2% 丢包下无累积花屏，10 秒内自愈
- [ ] MFCD 20 个边框键全部命中，误触率 < 2%
- [ ] DCS 跑无边框窗口时可用，全屏独占时给出明确告警而非黑屏

## 5. 范围护栏（Scope Guards）

每条护栏都是一次「如果破了，就会连锁失控」的判断。

| 护栏 | 破了会怎样 |
|---|---|
| 一期只做**一款机型**的完整 Profile | 同时铺多机型会让 widget 抽象永远定不下来 |
| MFCD 只做**像素流**，不做符号重绘 | 每个机型的符号系统都是黑盒，重绘是无底洞 |
| 不做**实体硬件** | 一旦碰 PCB，项目性质就变了 |
| iOS 不早于 P4 | 双端并行会让协议层反复返工 |
| 关键 HOTAS 不上平板 | 一旦被当成主操作设备，延迟问题会变成「产品不可用」 |
| **每个阶段结束必须冻结需求** | 不加「顺便做一下」的条目 |

## 6. 输入边界：什么该上平板，什么不该

这是产品边界，不是技术边界，但必须在 P2 之前写死。

**该上平板**（对 50 ms 延迟不敏感）：起落架、襟翼、减速板、UFC / CDU 输入、雷达模式、MFCD 边框键、通讯频率、检查单、灯光。

**不该上平板**（必须留在物理杆）：扳机、武器投放、干扰弹抛撒、配平、油门、杆量本身。WiFi 链路抖动 30–80 ms，且触摸屏没有行程反馈——按了不知道按没按到。

**FC3 级模块**（Su-27 / F-15C / MiG-29 / Su-33 / A-10A）没有 clickable 表，只能键位模拟。这类机型的产品定位是**只读仪表盘**，Profile 里用 `capabilities: ["readonly"]` 标记，客户端自动隐藏所有输入控件。

## 7. 风险登记

| 风险 | 概率 | 影响 | 早期信号 | 缓解 |
|---|---|---|---|---|
| 校园网全隔离且 Tailscale 打洞失败 | 中 | 高 | P0.6 实测 | 热点兜底；自建 VPS 中继 |
| DCS-BIOS 项目停滞 | 高 | 中 | 生成失败或版本不匹配 | `ClickableParser` 自研兜底 |
| 独占全屏无法捕获 | 高 | 中 | P3.2 首次尝试 | 强制无边框窗口 + 启动检测 |
| NVENC 不可用（老卡 / 核显） | 中 | 中 | 编码器枚举 | AMF / QSV / x264 三级兜底 |
| Android 低延迟解码碎片化 | 中 | 中 | P3.5 机型测试 | 机型白名单 + 软解降级 |
| 多人服务器禁导出 | 中 | 中 | P0.3 在服务器上失败 | 能力探测 + 只读降级 + 明确提示 |
| DCS 更新破坏导出脚本 | 高 | 中 | 每次版本更新 | 启动自检 + 自动重部署 + 版本戳 |
| 范围蔓延 | 极高 | 高 | 阶段中期冒出新需求 | §5 护栏 + 阶段冻结 |

## 8. 工作方式约定

- **每阶段结束必须有一个 60 秒的演示片段**，录屏存档。演示不了的阶段不算完成。
- **所有 DCS 相关测试必须有 mock 等价物**，否则 CI 会变成「只有本机能跑」。
- **录制的真实遥测入库**（`tests/fixtures/recording/`），让真机数据变成可重复输入。
- **每个阶段开始时先写退出准则的测试**，再写实现。退出准则里每一条都必须能被自动化或被明确的检查清单覆盖。
- **不做静默失败**：所有降级路径都必须有可见提示，宁可吵闹也不要装作正常。

## 9. 附录：术语

| 术语 | 含义 |
|---|---|
| **ControlRef** | 底座舱控件的抽象定义：标识符 + device_id + command_id + 类型 + 取值域 |
| **Profile** | 一份机型面板描述：页面、widget 实例、位置尺寸、绑定的 ControlRef |
| **Snapshot** | 某一帧的完整或增量状态集合 |
| **Cmd** | 一条输入指令：ControlRef 标识符 + 目标值 + 序号 + 时间戳 |
| **capabilities** | Profile 声明的能力集：readonly / readable / writable / video |
| **mock-export** | 按真实字段结构产生假数据的模拟导出源，用于脱离 DCS 开发 |
| **无边框窗口** | DCS 显示模式，像素捕获的前提 |
